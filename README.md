# PUBG Match Pipeline

PUBG 공식 API로 매치 데이터를 수집해 SQLite DB로 정리하고, 데이터 품질을 자동으로 점검한 뒤, SQL로 **부정행위 검토 후보**를 뽑는 파이프라인입니다.

- 매치 945개, 참가자 78,650명 수집 (분석 대상: 정규 squad 매치의 사람 플레이어 35,570명)
- 수집 → DB 구축 → 품질 점검(9개 항목) → SQL 분석을 `run_pipeline.py` 하나로 실행
- 품질 점검에 실패하면 분석 단계로 넘어가지 않음

## 파이프라인 구성

```
get_samples.py ─▶ collect_matches.py ─▶ build_db.py ─▶ validate.py ─▶ analyze_sql.py
 매치 ID 목록      매치 상세 JSON         SQLite DB      품질 점검 9개     sql/*.sql 실행
 (누적 저장)       (증분·재시도)          (원본으로 재생성)  실패 시 중단      검토 후보 CSV
```

| 단계 | 스크립트 | 하는 일 |
|---|---|---|
| 1. 매치 목록 | `get_samples.py` | `/samples`에서 최근 매치 ID를 받아 기존 목록에 **추가** (덮어쓰지 않음, 새 ID를 앞에 둠) |
| 2. 매치 상세 | `collect_matches.py` | 매치 JSON을 `data/`에 저장. 이미 받은 매치와 만료된 매치는 건너뜀, 429 응답은 대기 후 재시도 |
| 3. DB 구축 | `build_db.py` | 원본 JSON에서 DB를 매번 새로 만듦. 몇 번을 돌려도 같은 결과 |
| 4. 품질 점검 | `validate.py` | 원본 대조, 중복, 결측, 논리 오류 등 9개 항목을 통과/실패로 판정하고 `logs/`에 기록 |
| 5. 분석 | `analyze_sql.py` + `sql/` | SQL 파일을 순서대로 실행하고 검토 후보를 `output/review_candidates.csv`로 저장 |
| 전체 실행 | `run_pipeline.py` | 1~5단계를 순서대로 실행, 단계별 결과를 `logs/pipeline_날짜.log`에 기록 |
| 테스트 | `test_validate.py` | 점검 로직이 일부러 넣은 오류(누락, 중복, 논리 오류 등)를 잡아내는지 확인 (7개) |

초기 탐색 단계에서 쓴 스크립트(`get_match.py`, `check_*.py`, `analyze_outliers*.py`)는 과정 기록용으로 남겨 두었습니다.

## DB 스키마

```
matches       (match_id PK, game_mode, match_type, map_name, duration, created_at)
participants  (match_id, player_id, is_bot, kills, assists, dbnos, headshot_kills,
               damage_dealt, time_survived, walk_distance, ride_distance,
               win_place, kill_place)
              PK (match_id, player_id), FK match_id → matches
```

- `match_type`: official(일반), competitive(랭크), airoyale(봇전), trainingroom(훈련장), tutorialatoz(튜토리얼)
- `is_bot`: `player_id`가 `ai.`로 시작하면 1

## 데이터 품질 점검

### 자동 점검 (`validate.py`, 9개 항목 모두 통과)

| 항목 | 결과 |
|---|---|
| 원본 매치 수 = DB 매치 수 | 945 / 945 |
| 매치별 참가자 수가 원본과 일치 | 불일치 0건 |
| (매치, 플레이어) 중복 | 0건 |
| 참가자 0~1명 매치가 모두 훈련장·튜토리얼인지 | 원인 불명 0건 |
| 주요 컬럼 NULL / 음수 값 | 0건 / 0건 |
| 헤드샷 킬 > 킬 | 0건 |
| 생존 시간 > 매치 시간 + 10초 | 0건 |
| `is_bot`과 `player_id` 규칙 일치 | 불일치 0건 |

### 점검하면서 확인한 것

- **참가자 0명·1명 매치의 원인**: 원본 JSON을 열어 확인한 결과 실제 게임이 아니었습니다. 0명 매치 18개는 모두 `trainingroom`(훈련장, duration 0, 참가자 데이터 없이 asset만 있음), 1명 매치 41개는 모두 `tutorialatoz`(튜토리얼)였습니다. 이 규칙을 점검 항목으로 넣어서, 일반 매치에서 참가자가 0~1명이면 실패로 잡도록 했습니다.
- **봇이 참가자의 38%**: `player_id`가 `ai.`로 시작하는 참가자가 78,650명 중 29,544명이었습니다. 일반 매치와 봇전에는 봇이 있고 랭크 매치에는 0명이었습니다. 봇은 평균 피해량 92(사람 160), 헤드샷 비율 0.06(사람 0.24)으로 분포가 크게 달라서, 1차 분석(봇 포함)의 기준선이 왜곡되어 있었습니다.
- **봇을 빼도 분포는 치우쳐 있음**: 처음에는 피해량 Q1이 0인 이유가 봇이라고 추측했지만, 봇을 빼도 사람 중 0킬이 54%였고 Q1은 5.7이었습니다. 추측이 틀렸고, 원래 분포가 치우쳐 있는 것으로 정정했습니다.
- **매치 ID는 시간이 지나면 만료됨**: 처음 받은 ID 735개 중 265개만 조회됐고 470개는 404였습니다. 반면 받자마자 수집한 ID 680개는 모두 성공했습니다. 그래서 목록 수집 직후 상세 수집을 하도록 파이프라인을 묶었고, 404가 난 ID는 `expired_ids.txt`에 기록해 다시 요청하지 않습니다.
- **팀 구성은 모드 안에서도 가변적**: duo-fpp 매치 하나는 roster가 52개였는데(예상 50개), 확인해 보니 2인 팀 48개와 1인 팀 4개였습니다. 코드 문제가 아니라 실제 팀 구성이었습니다.

## 분석: 부정행위 검토 후보 찾기

### 정제 (`sql/01`, `sql/02`)

| 단계 | 남은 행 |
|---|---|
| 전체 참가자 | 78,650 |
| squad 모드만 | 51,390 |
| 정규 매치만 (봇전·훈련장·튜토리얼 제외) | 42,729 |
| 사람만 (봇 제외) | 35,570 |

### 1차 시도와 문제점

처음에는 squad 모드 피해량에 IQR 3배 기준을 적용했습니다(`analyze_outliers*.py`, 매치 50개 기준). 걸린 사람은 대부분 오래 살아남아 1위를 한 플레이어였습니다(순위 중앙값 1위, 생존 20.2분). 피해량이 높은 이유의 상당 부분이 생존 시간이었고, 봇도 섞여 있었습니다.

### 지표 설계

**최소 표본 조건이 필요한 근거** (`sql/04`): 킬 수 구간별로 헤드샷 비율 평균은 0.23 안팎으로 비슷하지만, 헤드샷 100%인 사람 비율은 1킬에서 23.1%, 5~9킬에서 0.2%입니다. 표본이 작으면 비율이 극단값으로 튀므로, 헤드샷 비율은 **킬 5 이상**인 경우만 썼습니다.

**매치 안에서 비교** (`sql/05`): 매치마다 로비 수준이 달라서, 분당 피해량을 같은 매치 사람들의 평균·표준편차와 비교한 z-score를 썼습니다(`AVG() OVER (PARTITION BY match_id)`). 5분 미만 생존자는 분모가 작아 제외했습니다. 이때 문제가 하나 나왔는데, 교전이 거의 없던 매치(참가자 98명 중 봇 64명, 사람 34명의 킬 합계 1개)에서는 분당 피해량 6.0이 z 5.57이 됐습니다. 그래서 **전체 상위 10%(분당 피해량 30.5 이상)** 라는 절대 하한을 함께 걸었습니다.

**신호끼리 독립인지 확인**: 처음에는 킬 수 상위 1%도 신호로 넣었는데, 후보가 전부 "분당 피해량 + 킬 수" 조합이고 대부분 1위였습니다. 상관계수를 보니 분당 피해량과 킬 수는 0.64로 같은 것(교전을 많이 함)을 두 번 세고 있었습니다. 반면 헤드샷 비율은 킬 수, 분당 피해량과 모두 -0.02로 거의 독립이었습니다. 그래서 킬 수 신호를 빼고 두 축으로 정리했습니다.

### 검토 후보 기준 (`sql/06`)

| 축 | 조건 |
|---|---|
| A. 교전량 | 분당 피해량이 같은 매치 대비 z ≥ 3 (비교 인원 20명 이상) **그리고** 전체 상위 10% |
| B. 정확도 | 헤드샷 비율 상위 5% (킬 5 이상 중, 헤드샷 비율 0.625 이상) |

두 축 모두 걸리면 "우선 검토", 하나만 걸리면 "일반 검토"입니다.

### 결과

| 구분 | 건수 | 순위 중앙값 | 킬 중앙값 |
|---|---|---|---|
| A만 (교전량) | 363 | 15위 | 4 |
| B만 (정확도) | 46 | 2위 | 6 |
| A와 B 모두 (우선 검토) | 0 | - | - |
| 합계 | 409 (35,570건 중 1.15%) | | |

- 시간과 매치 수준을 보정하니, 교전량 축 후보의 순위 중앙값이 1위에서 15위로 바뀌었습니다. 1차 시도처럼 "오래 살아서 이긴 사람"을 잡는 문제는 해결됐습니다.
- 두 축에 동시에 걸린 경우는 없었습니다. 공개 통계 범위에서는 교전량과 정확도가 함께 극단적인 플레이어-매치가 이 표본에 없었다는 뜻입니다.

### 한계

- **후보는 부정행위 판정이 아닙니다.** 상위 몇 %를 자르면 정상 플레이어도 항상 그만큼 걸립니다. 실제 운영이라면 리플레이 확인 등 다른 근거로 확인할 목록입니다. 그래서 후보 CSV는 저장소에 올리지 않았습니다.
- **플레이어 단위 추적이 어렵습니다.** `/samples`는 무작위 매치라서 같은 사람이 최대 3판만 나왔습니다(2판 이상 642명). 계정 단위로 행동 변화를 보려면 플레이어별 매치 이력 수집이 필요합니다.
- **매치 요약 통계만 썼습니다.** 명중률, 킬 거리, 반응 시간 같은 신호는 텔레메트리(이벤트 로그)가 있어야 계산할 수 있습니다.
- 임계값(z 3, 상위 10%, 상위 5%, 킬 5)은 분포를 보고 정했지만, 정답 라벨이 없어서 오탐률·탐지율은 측정하지 못했습니다.

오버워치처럼 공개 데이터가 없는 게임에 같은 방식을 적용하는 구상은 [docs/overwatch_extension.md](docs/overwatch_extension.md)에 정리했습니다.

## AI 활용 범위와 검증

이 프로젝트는 AI 코딩 도구를 적극적으로 활용해 진행했습니다.

- **1차 작업** (수집, DB 구축, 1차 품질 점검과 IQR 분석): Claude 채팅의 안내를 받아 각 단계를 직접 실행하고 결과를 확인했습니다.
- **2차 작업** (표본 확대, 자동화, 품질 점검 자동화, SQL 분석 재설계): Claude Code가 코드 작성, 실행, 결과 검증까지 주도했습니다.

| 구분 | 내용 |
|---|---|
| 직접 한 것 | API 키 발급과 실행 환경 구성, 1차 작업의 단계별 실행과 결과 확인, 지원 직무(안티치트)에 맞춘 프로젝트 방향 설정, 오버워치 확장 문서의 신호 가설과 오탐 사례(플레이 경험), 공개 범위 판단 |
| AI가 한 것 | 코드와 SQL 작성, 분석 설계, 결과 검증과 설계 수정 |

### 작업 중 데이터로 다시 확인해서 버리거나 고친 설계

AI가 처음 낸 결과를 그대로 쓰지 않고, 수치로 다시 확인해서 바꾼 사례입니다.

- IQR 기준 → 걸린 사람 대부분이 오래 살아남은 1위였음. 생존 시간 효과로 보고 분당 피해량으로 변경
- 킬 수 신호 → 분당 피해량과 상관 0.64라서 같은 것을 두 번 세는 것으로 판단하고 제외
- 매치 내 z-score 단독 사용 → 교전이 거의 없던 매치에서 z가 튀는 것을 확인하고 절대 하한 추가
- "Q1이 0인 건 봇 때문" → 봇을 빼고 다시 계산해 보니 Q1이 여전히 낮아서, 틀린 추측으로 정정

## 실행 방법

1. [PUBG Developer Portal](https://developer.pubg.com/)에서 API 키를 발급받습니다.
2. 프로젝트 폴더에 `.env` 파일을 만들고 키를 넣습니다.
   ```
   PUBG_API_KEY=발급받은_키
   ```
3. 패키지를 설치합니다.
   ```
   pip install requests python-dotenv
   ```
4. 전체 파이프라인을 실행합니다.
   ```
   python run_pipeline.py
   ```
5. 테스트를 실행합니다.
   ```
   python -m unittest test_validate.py
   ```

`.env`(API 키), `pubg.db`, `data/`, `output/`, `logs/`는 `.gitignore`로 저장소에서 제외했습니다.

### 자동 실행 (Windows 작업 스케줄러)

하루 한 번 실행하도록 등록하는 예시입니다. `/samples` ID는 시간이 지나면 만료되므로, 매일 받아서 바로 수집하면 표본이 계속 늘어납니다.

```
schtasks /create /tn "pubg-pipeline" /sc daily /st 09:00 /tr "python C:\경로\pubg-pipeline\run_pipeline.py"
```
